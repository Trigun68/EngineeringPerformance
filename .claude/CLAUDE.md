## 🌐 Языковые правила (Language Policy)
Строгое разделение языков для документации и технического контента.

| Тип контента | Язык | Примеры |
|---|---|---|
| **Документация** | 🇷🇺 Русский | `TECHNICAL.md`, `USER_MANUAL.md`, `CHANGELOG.md`, ADR, планы, отчёты, комментарии в коде (объясняющие «почему») |
| **Технические запросы** | 🇬🇧 English | Имена переменных, функций, классов; сообщения коммитов; названия веток; логи; ошибки; API-эндпоинты; SQL-запросы |
| **Код** | 🇬🇧 English | Синтаксис, типы, интерфейсы, тесты, конфиги |
| **Комментарии в коде** | 🇷🇺 Русский | Объяснение бизнес-логики, сложных решений, архитектурных выборов |

📌 **Правила применения:**
- Документация в `_doc/`, `_install/`, `docs/` → только на русском.
- Техническая документация (OpenAPI, GraphQL схемы, диаграммы) → английский допустим для терминологии, но описания — на русском.
- Сообщения коммитов: заголовок на английском (Conventional Commits), тело при необходимости — на русском.
- Имена задач в оркестрации (`AUTH-001`, `PAY-002`) → английский, описания задач в планах → русский.

## 📁 Структура проекта и размещение данных
Соблюдай строгую иерархию. Запрещено разбрасывать артефакты по корню или `src/` без чёткой цели. Организация `src/` выбирается согласно масштабу: **Feature-Based** (крупные независимые модули) или **Layer-Based** (малые проекты, строгие технические слои).

| Папка | Назначение | Правила |
|---|---|---|
| `tmp/` | Рабочие материалы, планы оркестрации, черновики, промежуточные логи | Создаётся при старте. **Автоочистка** после успешного завершения. Состояние оркестрации хранится здесь. |
| `_tmp/` | Следы незавершённых или аварийно прерванных сессий | Перенос содержимого `tmp/` при `Ctrl+C`, таймауте или критической ошибке. Удаляется вручную после анализа. |
| `_work/` | Суммированные отчёты по обработке запросов | Файл: `YYYYMMDD_HHMMSS_session_summary.md`. Создаётся **только** при успешном завершении. Содержит: цель, шаги, изменённые файлы, результаты тестов, риски. |
| `_doc/` | Обязательная проектная документация | Строго: `TECHNICAL.md`, `USER_MANUAL.md`, `ADMIN_MANUAL.md`, `CHANGELOG.md`. Расширяется оркестрацией: `plans/`, `issues/`, `architecture/`. **Обновление обязательно** при любом изменении логики, API, БД или UX. **Язык: русский**. |
| `_install/` | Артефакты развёртывания и инициализации | `_install/DEPLOY.md` → инструкция по установке. `_install/db/` → схемы, данные, миграции. **Язык инструкций: русский**. |
| `_install/db/` | База данных: схемы, данные, тестовые наборы | `schema.sql` + `migrations/`. `seed.sql` + `migrations_data/`. `test_data.sql`. Миграции только через ORM/CLI. Ручное редактирование запрещено. |
| `config/` | Внешние конфигурации | `.env.example` обязательно. Валидация при старте (Zod/Pydantic). |
| `scripts/` | Утилиты, CI-хелперы, одноразовые задачи | Идемпотентность. Вывод в `stdout`/логи. Запрет `rm -rf`, `DROP DATABASE`, прямых сетевых вызовов. |

🔒 **Правила данных:**  
Секреты → только в `.env` или менеджере секретов. Крупные бинарники → `.gitignore` / Git LFS. Пути только относительные.

## 📋 Правило CHANGELOG (обязательное)

**Каждое изменение кода, затрагивающее логику, UI, API, БД или тесты — должно быть отражено в `docs/changelog/CHANGELOG.md` в разделе `[Unreleased]`.**

Правила оформления записи:
- Формат: `- <Компонент/файл>: <что изменилось и зачем>` — одной строкой на русском.
- Группировать по смысловым блокам с заголовком (например: `### Added`, `### Changed`, `### Fixed`).
- Запись добавляется **в том же шаге**, что и изменение кода — не после, не в конце сессии.
- Не добавлять запись только для: правок опечаток/форматирования без смысловых изменений, обновлений `tmp/`/`_work/` файлов.

❌ Нарушение: изменён код → CHANGELOG не обновлён.  
✅ Норма: изменён код → в тот же момент добавлена запись в `[Unreleased]`.

## 📝 Принципы документирования (Documentation Principles)
Документация управляется через конфигурацию и следует гибридной модели: временное состояние (workspace) vs перманентные артефакты.

1. **Конфигурируемые пути**  
   Никогда не хардкодь пути к документации. Читай их из `.cursor/config.json` или используй дефолты проекта (`_doc/`, `_work/`).  
2. **Структура по назначению**  
   - `plans/` → Высокоуровневые планы (что строить)  
   - `reports/` ↔ `_work/` → Итоговые отчёты (что сделано)  
   - `issues/` → Техдолг и известные проблемы (не блокируют текущую работу)  
   - `features/` / `api/` / `components/` / `architecture/` → Детальная документация  
3. **Гайдлайны наполнения**  
   - Один файл = одна тема/фича. Не смешивать контексты.  
   - Всегда добавлять дату обновления и ссылку на исходный код.  
   - Использовать кросс-ссылки между связанными документами.  
   - Архивировать устаревшие разделы, не удалять их бесследно.  
4. **Нейминг файлов**  
   - Фичи/планы: `feature-name.md` (kebab-case)  
   - Компоненты: `ComponentName.md` (PascalCase)  
   - Проблемы: `ISS-NNN-description.md`  
5. **Триггеры обновления**  
   - **Авто:** после завершения оркестрации, после фиксов багов, после ADR.  
   - **Ручно:** по команде `/documenter` или явному запросу пользователя.  
6. **Язык документации**  
   - Весь пользовательский и технический контент документации → **русский язык**.  
   - Термины, аббревиатуры, названия технологий → сохраняются на английском (JWT, OAuth, API, CI/CD).

## 📋 Планирование и управление задачами (Task Planning & Tracking)
Оркестрация использует двухуровневую систему отслеживания: метаданные состояния (временные) + контент (перманентный).

1. **Идентификаторы оркестрации**  
   Формат: `orch-YYYY-MM-DD-HH-mm-{slug}` (пример: `orch-2026-02-10-15-30-auth`).  
2. **Состояние сессии (Workspace)**  
   Хранится в `tmp/active/{id}/`: `progress.json` (общий статус, счётчики), `tasks.json` (статусы задач), `links.json` (ссылки на `_doc/`).  
   При крахе/таймауте → автоматический перенос в `_tmp/` для последующего `resume`. Автоочистка завершённых сессий через 7 дней.  
3. **Лимиты и управление контекстом**  
   - Максимум **10 задач** за один цикл оркестрации. При превышении → пауза, отчёт прогресса, запрос продолжения.  
   - При приближении к лимиту токенов → сохранение состояния в `tmp/`, явный запрос на продолжение.  
4. **Статусы оркестрации и задач**  
   - Оркестрация: `🔵 planning` → `🟢 ready` → `🟡 in-progress` → `🟠 documenting` → `✅ completed` / `❌ failed`  
   - Задача: `⏳ pending` → `🔄 in-progress` → `✅ completed` / `🚫 blocked`  
5. **Идентификаторы задач**  
   Формат: `PREFIX-NNN` (AUTH, PAY, API, UI, DB, REF, TEST). Пример: `AUTH-001`, `API-003`.  
6. **Язык описаний задач**  
   - ID задач, префиксы, технические метки → английский.  
   - Описания задач в планах, отчётах, комментариях → **русский язык**.

## 🔄 Правила обработки запросов (Workflows)
Выбор рабочего процесса определяется сложностью задачи. ИИ обязан строго следовать выбранному циклу.

### 🟢 Простые задачи: `/implement` (Code → Test → Docs)
**Применение:** 1–2 файла, фиксы, компоненты, утилиты, правки конфига.
1. `worker` → генерация кода.
2. `test-runner` → запуск тестов (если есть в проекте).
   - При падении: вызов `debugger` (макс. 2 попытки) → повтор `test-runner`.
   - Если тестов нет → шаг пропускается.
3. `documenter` → создание/обновление документации **на русском языке**.
4. Коммит + отчёт в `_work/` + очистка `tmp/`.

### 🟡🔴 Сложные задачи: `/orchestrate` (Plan → Loop → Docs)
**Применение:** Полноценные фичи, мульти-модули, рефакторинг, архитектура, миграции, безопасность.
1. **Phase 1: Планирование** → `planner` разбивает задачу на подзадачи (макс. 10 за цикл). План сохраняется в `tmp/plan.md` и линкуется в `_doc/plans/` **на русском**.
2. **Phase 2: Цикл задач** (для каждой подзадачи):
   - `worker` → реализация.
   - `test-runner` → линт + тесты + проверка acceptance criteria.
     - ❌ Ошибка/неполнота → `debugger` (макс. 3 попытки) → повтор.
   - `security-auditor` → проверка (аутентификация, ввод данных, секреты, платежи).
   - `reviewer` → проверка качества кода и архитектуры.
     - ❌ Замечания → `debugger` (макс. 3 попытки) → повтор.
   - ✅ Успех → статус задачи `completed`, переход к следующей.
3. **Phase 3: Документация** → `documenter` формирует итоговый отчёт **на русском**, сохраняет в `_work/`. Очистка `tmp/`.
⚠️ *Лимит контекста:* при приближении к лимиту → сохранение состояния в `_tmp/`, запрос продолжения у пользователя.

## 🏛 Архитектурные принципы (Architecture Principles)
Применяются на этапах планирования, реализации и ревью.

| Принцип | Ключевые правила |
|---|---|
| **SOLID** | SRP (один модуль = одна причина изменения), OCP (открыто для расширения, закрыто для модификации), LSP (подтипы не ломают контракт), ISP (узкие интерфейсы), DIP (зависим от абстракций). |
| **Слои (SoC)** | Presentation → Application → Domain → Data → Infrastructure. Верхние слои зависят только от нижних. Бизнес-логика изолирована от инфраструктуры. |
| **Паттерны** | **Repository** (абстракция доступа к данным), **Service** (бизнес-логика), **Factory** (создание объектов), **Strategy** (взаимозаменяемые алгоритмы). |
| **Dependency Injection** | Внедрение зависимостей через конструктор. Запрет `new` внутри классов. Обеспечивает слабую связность и тестируемость. |
| **Производительность** | Индексы, пагинация, connection pooling, избегание N+1, кэширование на правильном слое, async/await для I/O, очистка ресурсов, таймауты. |
| **Тестирование** | Пирамида: Unit (много) → Integration (некоторое) → E2E (мало). Бизнес-логика тестируется изолированно. |
| **Анти-паттерны** | ❌ God Object, Spaghetti Code, Magic Numbers, Circular Dependencies, Premature Optimization. |

## 🔍 Стандарты качества кода (Code Quality Standards)
Применяются `worker`, `reviewer` и `debugger` на каждом шаге генерации.

| Категория | Правила |
|---|---|
| **Читаемость** | Понятные имена (англ.), функции ≤ 30 строк, один уровень абстракции на функцию. Комментарии **на русском** объясняют «почему», а не «что». |
| **DRY / KISS / YAGNI** | Выноси общую логику. Простое решение лучше сложного. Не добавляй функционал «на будущее». |
| **Code Smells & Refactoring** | Длинный метод → Extract Method. Большой класс → Split (SRP). Много параметров → Parameter Object. Примитивная одержимость → Value Objects. Дублирование → Shared Utils. |
| **Best Practices** | Специфичные типы ошибок (`ValidationError`, `NotFoundError`). Явная обработка `null`. Иммутабельность (копирование вместо мутации). Чистые функции (без сайд-эффектов). |
| **Метрики сложности** | Cyclomatic Complexity: 1–5 (норма), 6–10 (умеренно), 11–20 (высоко, рефакторинг), 21+ (критично, обязателен рефакторинг). |

## 🧠 Оркестрация задач по сложности

| Уровень | Критерии | Протокол действий ИИ |
|---|---|---|
| 🟢 **Low** | 1–2 файла, фиксы, мелкие утилиты | `/implement` → Code → Test (max 2 fix) → Docs (RU) → Атомарный коммит → `_work/` + очистка `tmp/`. |
| 🟡 **Medium** | 3–5 файлов, новый модуль, интеграция, рефакторинг | `/orchestrate` (≤10 задач) → Plan (RU) → Loop (Worker → Test → Review) → Docs (RU) → PR с тестами → `_work/` + очистка `tmp/`. |
| 🔴 **High** | Архитектура, БД, CI/CD, безопасность, `BREAKING CHANGE` | `/orchestrate` → ADR в `_doc/adr/` (RU) → **Запрос подтверждения** → Поэтапная реализация с Security/Review → Полный прогон → `_doc/` & `_install/` (RU) → PR → `_work/` + очистка `tmp/`. |

📌 **Правила оркестрации:**
- Всегда объявляй уровень: `[🟢 Low]`, `[🟡 Medium]`, `[🔴 High]`.
- Для `🔴 High` запрещено менять `main` напрямую. Только ветка + PR.
- При изменении структуры/зависимостей → сначала обнови `tech.md` / `CLAUDE.md`.
- Статусы: `✅ завершено`, `⏸️ требует ручной проверки`, `❌ ошибка: ...`.
- Файлы из `tmp/` при ошибке/прерывании не удаляются, переносятся в `_tmp/`.

## 🌿 Версионирование и Git-практики (Git & Versioning)
Любое изменение кода, конфигов или документации обязательно фиксируется в Git. Процесс обогащён правилами безопасности и автоматизации.

### Инициализация и настройка
Репозиторий: `.git/` в корне решения. Ветка по умолчанию: `main`.

### Workflow после успешной реализации

**Шаг 1 — проверка перед коммитом:**
```bash
git status                                      # что изменилось
dotnet build EngineeringPerformance.slnx        # сборка green
dotnet test EngineeringPerformance.slnx         # все тесты green
```

**Шаг 2 — стейджинг:**
```bash
git add .                                       # или точечно: git add <file>
git status                                      # финальная проверка
```

**Шаг 3 — коммит (Conventional Commits):**
```bash
git commit -m "feat(scope): subject"
# тело коммита при необходимости — русский язык
```

**Шаг 4 — пуш:**
```bash
git push origin <branch>
```

### Именование веток

| Тип | Шаблон | Пример |
|-----|--------|--------|
| Новая фича | `feat/<description>` | `feat/projects-page` |
| Баг-фикс | `fix/<description>` | `fix/performance-filter` |
| Рефакторинг | `refactor/<description>` | `refactor/data-import` |
| Документация | `docs/<description>` | `docs/git-workflow` |
| Задача/обслуживание | `chore/<description>` | `chore/update-deps` |

### Типы коммитов

| Тип | Когда |
|-----|-------|
| `feat(scope)` | новая функциональность (фича, UI, сервис) |
| `fix(scope)` | исправление бага |
| `refactor(scope)` | рефакторинг без изменения поведения |
| `test(scope)` | добавление/изменение тестов |
| `docs(scope)` | документация, CHANGELOG, `.md` файлы |
| `chore(scope)` | зависимости, конфиги, инфраструктура |
| `perf(scope)` | оптимизация производительности |

**Scopes проекта:** `app`, `core`, `infra`, `tests`, `db`, `ui`, `docs`, `config`

### Правила коммита

- Заголовок: **английский**, строчные, без точки, ≤ 50 символов
- Тело (опционально): **русский**, объясняет «почему», не «что»
- Каждый коммит компилируется и тесты проходят
- `docs/changelog/CHANGELOG.md` обновляется **в том же коммите**, что и код
- При изменении схемы БД — миграция и SQL-скрипт в одном коммите с кодом

### Ветковая стратегия

```
main          ← production-ready, теги v1.x.x
  └── feat/*  ← фичи, мержатся через PR
  └── fix/*   ← фиксы, мержатся через PR
```

- **Прямой пуш в `main` запрещён** (только через PR/merge)
- `rebase` — для локальных веток перед PR
- `merge --no-ff` — для интеграции в `main`

### Теги релизов (SemVer)

```bash
git tag -a v1.0.0 -m "Первый релиз"
git push origin --tags
```

`BREAKING CHANGE:` в теле коммита → мажорный релиз (v2.0.0).

⛔ **Запрещено:**
- `git push --force` в `main`
- Коммитить `bin/`, `obj/`, `.vs/`, `*.user`, `tmp/`, секреты
- Коммитить без прохождения `dotnet test`

## 🤖 AI Instructions

3. **Архитектура:** при изменении структуры сначала опиши план в `tmp/session_plan.md`, для `🔴 High` запроси подтверждение.
4. **Стиль:** следуй линтер-конфигам, `tsconfig`/`pyproject`, принципам SOLID, DRY, KISS, YAGNI.
