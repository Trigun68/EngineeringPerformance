# ISS-019: `page-data` отдаёт ~50 МБ JSON на одну версию проекта

**Статус:** 🔵 Backlog (2026-08-17)
**Категория:** Performance / API
**Приоритет:** P0 (High)
**Источник:** замеры в рамках ISS-018

## Контекст
Замер на demo-проекте (`GET /api/projects/1/versions/2/page-data`):

| Метрика | Значение |
|---------|----------|
| Сырой JSON | **50.6 МБ** |
| После gzip (включён в ISS-018) | 2.24 МБ |
| Строк в `forecast.detail` / `fact.detail` | 14 620 в каждой |
| Доля detail-гридов | 39.3 МБ из 50.6 МБ |

Профиль одной строки `detail` (36 полей):

| Поле | Объём по всем строкам | Замечание |
|------|----------------------|-----------|
| `estimationBasis` | 4.12 МБ | у большинства строк пусто |
| `catalogName` | 1.14 МБ | ↴ |
| `itemName` | 1.14 МБ | те же значения, что и `catalogName` |
| `pvName` | 1.14 МБ | те же значения, что и `catalogName` |
| `factLaborHours`, `factProductivity`, `zScore` | — | всегда `null` в прогнозном гриде |

Gzip (ISS-018) снял остроту на транспорте, но остаётся: сериализация и десериализация 50 МБ на
каждый cold-запрос (~2-3 с CPU), пик памяти на сервере, разбор JSON и построение грида в браузере.

## Направления решения
1. **Убрать дубли полей.** `catalogName` / `itemName` / `pvName` — одно и то же значение;
   оставить одно поле, остальные вычислять на клиенте.
2. **Не слать заведомо пустые колонки.** Для прогнозного грида `fact*`/`zScore` всегда `null`.
3. **Серверная пагинация / виртуализация detail-гридов** либо отдельный endpoint детализации,
   загружаемый по открытию вкладки, а не в общем батче `page-data`.
4. **Оценить бинарный формат** (например, сжатый columnar) для detail, если п. 1-3 недостаточно.

## Acceptance Criteria
- [ ] Сырой ответ `page-data` на demo-проекте < 10 МБ.
- [ ] Вкладка «Детально» открывается без полной перезагрузки батча.
- [ ] `perf-smoke.sh` укладывается в ужесточённые бюджеты (cold ≤ 4000 мс).
