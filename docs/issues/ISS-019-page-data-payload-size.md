# ISS-019: `page-data` отдавал ~50 МБ JSON на одну версию проекта

**Статус:** ✅ Решено (2026-08-18)
**Категория:** Performance / API
**Приоритет:** P0 (High)
**Источник:** замеры в рамках ISS-018

## Контекст
Замер на demo-проекте (`GET /api/projects/1/versions/2/page-data`):

| Метрика | Значение |
|---------|----------|
| Сырой JSON | **48.2 МБ** |
| После gzip (ISS-018) | 2.24 МБ |
| Строк в `forecast.detail` / `fact.detail` | 14 620 в каждой |
| Доля detail-гридов | 35.4 МБ из 48.2 МБ |

Gzip снял остроту на транспорте, но оставалась сериализация и десериализация 50 МБ на каждый
запрос, пик памяти на сервере и разбор JSON в браузере.

## Что оказалось внутри
Разбор payload показал, что объём создают не данные, а повторы.

| Источник объёма | Вклад | Замечание |
|---|---|---|
| Имена ключей JSON | **13.9 МБ** | 36 полей × 29 240 строк — 29% detail |
| Значения | 21.5 МБ | из них строки берутся из крошечных справочников |

Уникальных значений на 29 240 строк: `estimationBasis` — **5** (одно из них ~200 символов и
встречается 17 тысяч раз, 5.4 МБ), `catalogResource` — 2, `bindingType` — 3, `iicGroupName` — 16,
`facilityName` — 112, `catalogName` — 1609.

Также подтвердились совпадающие по значению поля (`catalogName` = `itemName` = `pvName`,
`catalogCode` = `pvCode`, `interpretation` = `tag`), но **удалять их не стали**: равенство
выполняется на текущих данных, а не гарантируется контрактом, и выводить одно поле из другого
значило бы испортить строки, где они законно различаются. Замер показал, что удаление дало бы
лишь 6.3 → 4.8 МБ — цена риска не оправдана.

## Решение: колоночный формат со словарями строк
Ответ `page-data` отдаёт гриды «Детально» в упакованном виде (`EncodedGridDto`):

```jsonc
"detail": {
  "columns": ["rowId", "facilityCode", ...],   // имена полей — один раз
  "strings": { "catalogName": ["…", "…"] },     // повторяющиеся строки — один раз
  "rows": [[224561, 0, 3, ...], ...]            // в ячейке остаётся индекс
}
```

Преобразование **обратимое и не знает бизнес-смысла полей**: набор и значения полей те же,
клиент восстанавливает те же объекты строк. Колонка попадает в словарь, только если уникальных
значений хотя бы втрое меньше числа строк, иначе словарь дороже экономии.

Границы изменения:
- внутренний `ProjectsPageDataDto` **не менялся** — на нём построены экспорты Excel/PDF (18 мест);
- упаковка живёт только на HTTP-границе (`ProjectsPageDataEncodedDto`);
- клиент распаковывает в `fetchProjectsPageData`, поэтому гриды, колонки и контекстные меню
  про кодирование не знают.

Упакованный вид кэшируется **отдельным ключом** (`page-data-encoded-v2:…`). Неупакованный DTO
в Redis не пишется. Без отдельного ключа warm-запрос читал бы из кэша 50 МБ и паковал заново
на каждый вызов — первый замер дал 2.3 с против прежних 1.24 с, то есть трафик экономился за счёт CPU.

HTTP-контракт с 2026-08-19: `GET page-data` и `GET /compare` не включают строки «Детально»;
они приходят с `GET page-data/detail` и `GET /compare/detail` при открытии вкладки.

## Результат

| Метрика | Было | Стало |
|---|---|---|
| Сырой JSON | 48.2 МБ | **6.47 МБ** (в 7.4 раза меньше) |
| Передано по сети (gzip) | 2.24 МБ | **1.07 МБ** |
| `page-data` warm | 1.24 с | **0.43–0.87 с** |
| `perf-smoke.sh` | — | все бюджеты зелёные |

## Acceptance Criteria
- [x] Сырой ответ `page-data` на demo-проекте < 10 МБ — **6.47 МБ**.
- [x] Вкладка «Детально» догружает строки отдельным запросом; «Итого» / «По объектам» не ждут detail.
- [x] `perf-smoke.sh` укладывается в бюджеты (`page-data` cold 352 мс, warm 434 мс).

## Проверка
- Round-trip тест кодировщика: `DetailGridEncoderTests` (5 тестов), в том числе случай, когда
  «дублирующие» поля различаются.
- Декодер клиента: `decodeEncodedGrid.test.ts` (5 тестов).
- Ручная проверка в браузере: гриды прогноза и факта «Детально» отрисовали декодированные
  строки; арифметика сходится (`производительность × количество = базовые часы`), то есть
  порядок колонок не нарушен.

## Осталось за рамками
- Серверная пагинация detail-гридов не потребовалась: ленивый `page-data/detail` снимает вес
  с первого экрана; полный encoded-батч ~6.5 МБ укладывается в бюджет `perf-smoke`.
