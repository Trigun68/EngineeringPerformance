# ADR-003: Расширение уникального ключа `ProjectPhysicalVolume`

**Дата:** 2026-05-10
**Статус:** Принято (после явного подтверждения пользователя)
**Авторы:** Elise

---

## Контекст

Сущность `ProjectPhysicalVolume` (таблица `ProjectPhysicalVolumes`) изначально имела уникальный составной индекс по тройке `(ProjectAnalysisVersionId, ProjectId, PhysicalVolumeId)`.

Это правило подразумевало бизнес-семантику: «на одну версию одного проекта допустима ровно одна строка для каждой номенклатуры физ. объёма». Для импортных потоков это работало, поскольку справочник `PhysicalVolumes` нормализован — для каждой реальной работы создавался отдельный элемент справочника с уникальным `Code`.

В итерации ISS-003 (контекстное меню детальной сетки прогнозирования) был добавлен сценарий ручного создания/копирования строки `ProjectPhysicalVolume` через UI-диалог. Пользователь обнаружил несоответствие модели реальной бизнес-логике:

> «Такая проверка должна происходить на уровне номенклатуры и объекта. Могут быть разные объекты с одинаковыми физ. объёмами».

Бизнес-кейс: на разных строительных объектах в рамках одного проекта/версии могут быть несколько работ с одной и той же номенклатурой физ. объёма (например, «кабель 1.5 мм²» используется и в `Здание линии стана 11-0515-02-01`, и в `Корпус ЦГП 11-0515-02-02`). Текущий уникальный индекс блокировал второй INSERT.

## Решение

**Расширить уникальный составной индекс** до 6 колонок:

`UNIQUE(ProjectAnalysisVersionId, ProjectId, PhysicalVolumeId, FacilityCode, FacilityName, WorkId)`

| Поле | Бизнес-смысл |
|---|---|
| `ProjectAnalysisVersionId` | Версия анализа проекта (срез данных) |
| `ProjectId` | Сам проект |
| `PhysicalVolumeId` | Номенклатура (FK на справочник `PhysicalVolumes`) |
| `FacilityCode` | Код объекта внутри проекта |
| `FacilityName` | Наименование объекта (из импорта) |
| `WorkId` | ID работы из источника данных |

### Новая бизнес-семантика

> «На одну версию проекта допустима ровно одна строка для каждой комбинации (номенклатура × код объекта × наименование объекта × ID работы)».

Это позволяет:
- Хранить одну номенклатуру в нескольких объектах.
- Хранить одну номенклатуру для нескольких работ на одном объекте.
- Запретить случайный дубликат полностью идентичной строки в одном проекте/версии.

### Семантика NULL

В SQL Server `UNIQUE` индекс рассматривает `NULL = NULL` как совпадение, т. е. множественные NULL в любом из полей блокируют дубликаты. На практике поля `FacilityCode`/`FacilityName`/`WorkId` приходят из импорта и почти всегда заполнены. Если в будущем потребуется ослабить ограничение — добавить filtered index с `WHERE [FacilityCode] IS NOT NULL AND ...`.

## Альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Оставить старый индекс `(Version, Project, PhysicalVolume)` | Блокирует валидный бизнес-сценарий (ISS-003 функция «копирование» полностью неработоспособна) |
| Включить `FacilityCode` без `FacilityName` и `WorkId` | Неполно: один объект может иметь несколько работ с одной номенклатурой |
| Включить ВСЕ контекстные поля (`CatalogId`, `Tag`, `BindingType`, `DocumentSet`, `EstimationBasis`) | Слишком широко: фактически отключает уникальность; имена объектов и ID работ — достаточный естественный ключ для бизнес-логики |
| Filtered unique index с `WHERE ... IS NOT NULL` | Допускает дубликаты при NULL — на текущих данных не оправдано (поля всегда заполнены при импорте). Усложняет миграцию |
| Сделать индекс не уникальным | Теряется защита от случайных дубликатов при ручном создании через UI |

## Последствия

### Положительные

- ✅ Сценарий «Добавить строку копированием выбранной» (ISS-003 пункт 2) работоспособен — пользователь может скопировать всю строку и поменять `FacilityCode` или `WorkId`.
- ✅ Сценарий «Добавить строку» (ISS-003 пункт 3) работоспособен.
- ✅ Защита от полностью идентичных дубликатов остаётся (через расширенный ключ).
- ✅ Импорт данных не ломается — новый индекс шире старого, любые данные, проходившие старую проверку, проходят новую.

### Отрицательные / риски

- ⚠ Размер ключа индекса в байтах: `int×3 (12) + nvarchar(100)+nvarchar(500)+nvarchar(200) = 12 + 200+1000+400 = 1612 bytes`. Это укладывается в лимит NONCLUSTERED INDEX (1700 bytes) для современного SQL Server, но близко к границе. Если в будущем увеличится `FacilityName` (`HasMaxLength(500)`) — потребуется review.
- ⚠ Производительность INSERT: новый индекс шире на 3 nvarchar-колонки. Для типового объёма данных (тысячи строк на версию) — несущественно.
- ⚠ BREAKING change на уровне БД: после применения миграции невозможно откатиться на старый индекс без ручного ENT-DROP (если в данных появятся «дубликаты по PV» с разными FacilityCode).
