# Отклик приложения: неблокирующий UI и кэш аналитики

Дата обновления: 2026-08-18. Связано: `docs/issues/ISS-018-perf-nonblocking-ui-and-cache.md`,
`docs/issues/ISS-019-page-data-payload-size.md`.

## Правило блокировки интерфейса

| Тип операции | Индикатор | Компонент |
|--------------|-----------|-----------|
| Чтение данных (гриды, отчёт, справочники) | Тонкая полоса в самой панели | `PanelBusyBar` |
| Мутация и экспорт (сохранение, PDF/Excel) | Полноэкранный оверлей | `WorkingOverlay` |

`WorkingOverlay` блокирует весь экран, поэтому применяется **только** там, где параллельная работа
пользователя недопустима. Любая загрузка данных обязана использовать `PanelBusyBar`: шапка,
вкладки и уже загруженные наборы остаются доступными, пока догружается остальное.

`PanelBusyBar` резервирует высоту полосы всегда, поэтому появление индикатора не сдвигает вёрстку,
и включается с задержкой (по умолчанию 300 мс) — быстрые ответы не мигают.

## Стартовый бандл

- Ленивые маршруты (`React.lazy` + `Suspense` в `App.tsx`): аналитика, справка, админка,
  настройки, журнал действий.
- Ленивые графики: `CompareChartView` (вкладка «Сравнение» → режим диаграммы),
  `NormBandChart` (модалка редактирования нормы). Highcharts не грузится, пока график не нужен.
- `manualChunks` в `vite.config.ts`: `highcharts`, `aggrid`, `mui` — отдельные кэшируемые чанки.

Проверка после сборки: в `dist/index.html` должны быть `modulepreload` только на `mui` и `aggrid`;
появление там `highcharts` означает, что кто-то импортировал график статически.

## Сжатие ответов

Nginx (`client/nginx.conf`) сжимает JSON и статику: `gzip on`, уровень 5, от 1 КБ,
`gzip_proxied any` (иначе ответы от backend через proxy не сжимаются).

Замер на demo-проекте:

| Ресурс | Без сжатия | gzip |
|--------|-----------|------|
| `GET .../page-data` | 6.47 МБ | 1.07 МБ |
| `assets/index-*.js` | 2.21 МБ | 618 КБ |

## Упаковка гридов «Детально»

Гриды «Детально» — десятки тысяч строк по 36 полей. В обычном JSON имена ключей весили больше,
чем данные, а строковые значения приходили из справочников в полторы тысячи значений, поэтому
ответ разрастался до 48 МБ. Такие гриды передаются колоночно (`EncodedGridDto`): имена полей —
один раз, повторяющиеся строки — словарём, в ячейке индекс. Итог 48.2 → 6.47 МБ
(см. `docs/issues/ISS-019-page-data-payload-size.md`).

Кодирование чисто транспортное и обратимое: набор и значения полей не меняются.

| Слой | Где живёт |
|------|-----------|
| Упаковка | `DetailGridEncoder`, только на HTTP-границе (`ProjectsPageDataEncodedDto`) |
| Распаковка | `decodeEncodedGrid` внутри `fetchProjectsPageData` |
| Экспорты Excel/PDF | работают с исходным `ProjectsPageDataDto`, он не менялся |

Гриды, колонки и контекстные меню про кодирование не знают — контракт `ProjectsPageDetailRow`
прежний. **Новое поле в `ProjectsPageDetailRowDto` нужно добавить и в список колонок
`DetailGridEncoder`**, иначе оно просто не доедет до клиента; round-trip тест это ловит.

## Кэш тяжёлых чтений

`IProjectAnalyticsCache` (реализация `ProjectAnalyticsCache` над `IDistributedCache`).

| Что кэшируется | Ключ | TTL |
|----------------|------|-----|
| `GET .../page-data` (9 гридов) | `page-data:v{versionId}:c{compareVersionId}` | 10 мин |
| `GET /projects/{id}/performance-report` | `report:p{planVersionId}:f{factVersionId}` | 10 мин |

Полный ключ в кэше — `analytics:p{projectId}:g{globalGen}.{projectGen}:{key}`. Инвалидация
инкрементирует поколение, старые записи становятся недостижимыми и истекают сами: перебирать
ключи Redis не нужно.

### Кто сбрасывает кэш

| Действие | Область |
|----------|---------|
| Импорт Excel (успешный) | Проект |
| CRUD ПОВ / трудоёмкости / оборудования (`ProjectDataService`) | Проект |
| Сохранение планового объёма прогноза | Проект |
| Пересчёт версии (`AnalysisVersionRecalculationOrchestrator`) | Проект |
| Создание / правка / архив / разархив / primary / копирование версии | Проект |
| CRUD норм ИИС | Все проекты |

**При добавлении нового пути записи данных проекта** обязательно вызвать
`IProjectAnalyticsCache.InvalidateProjectAsync` — иначе UI покажет старые цифры до истечения TTL.

Недоступность Redis не ломает чтение: ошибка логируется как warning, ответ считается заново.

## Контроль latency

```bash
./scripts/perf-smoke.sh http://localhost:8081
PERF_STRICT=0 ./scripts/perf-smoke.sh            # только предупреждения
BUDGET_PAGE_DATA_WARM=1500 ./scripts/perf-smoke.sh
```

Скрипт измеряет каждый кэшируемый endpoint дважды (cold / warm) и завершается с ненулевым кодом
при превышении бюджета. Бюджеты по умолчанию — в шапке скрипта; warm-бюджет заметно строже
cold-бюджета, поэтому сломанная инвалидация или отключённый кэш видны сразу.

Отдельно проверяется **размер** несжатого `page-data` (`BUDGET_PAGE_DATA_MB`, по умолчанию 12 МБ):
сжатие маскирует раздутый payload, а разбирать его всё равно клиенту. Если упаковка гридов
«Детально» сломается, ответ вернётся к ~48 МБ и проверка упадёт, даже когда время в бюджете.
