# 📖 Context & AI Rules (Unified) — v4.1 (Angular)

Этот файл автоматически подхватывается AI-агентами и разработчиками. Детальные требования к стеку, тестам и конфигурациям вынесены в соседние файлы (`tech.md`, `test.md`, `code.md`).  
🤖 **Инструкция для ИИ:** при старте сессии обязательно прочитай этот файл. Следуй описанным workflow, архитектурным принципам и языковой политике без отклонений.

## 🌐 Языковые правила (Language Policy)
Строгое разделение языков для документации, кода и технических артефактов.

| Тип контента | Язык | Примеры |
|---|---|---|
| **Документация & Планы** | 🇷🇺 Русский | `_doc/`, `_work/`, ADR, отчёты, комментарии в коде |
| **Код & Технические артефакты** | 🇬🇧 English | Имена классов/методов, переменные, коммиты, ветки, логи, API, SQL |
| **Комментарии в коде** | 🇷🇺 Русский | Объяснение бизнес-логики, архитектурных выборов, «почему» |
| **Коммиты & PR** | 🇬🇧 English (заголовок), 🇷🇺 Русский (описание при необходимости) | `feat(auth): add JWT refresh` / Описание задачи на русском |

📌 **Правила:**
- Документация в `_doc/`, `_install/`, `_doc/` → только на русском.
- Техническая документация (OpenAPI, схемы) → термины на английском, описания на русском.
- Имена задач в оркестрации (`AUTH-001`) → английский, описания в планах → русский.

## 📁 Структура проекта и размещение данных
Соблюдай строгую иерархию. Запрещено разбрасывать артефакты по корню без чёткой цели.

| Папка | Назначение | Правила |
|---|---|---|
| `tmp/` | Рабочие материалы, планы оркестрации, черновики | Автоочистка после успеха. Состояние сессии хранится здесь. |
| `_tmp/` | Следы незавершённых/аварийных сессий | Перенос из `tmp/` при крахе. Удаляется вручную после анализа. |
| `_work/` | Суммированные отчёты по обработке запросов | `YYYYMMDD_HHMMSS_session_summary.md`. Только при успехе. |
| `_doc/` | Обязательная проектная документация | `TECHNICAL.md`, `USER_MANUAL.md`, `ADMIN_MANUAL.md`, `CHANGELOG.md`, `plans/`, `issues/`, `architecture/`, `adr/`. **Обновление обязательно**. Язык: русский. |
| `_install/` | Артефакты развёртывания | `_install/DEPLOY.md` → инструкция. `_install/db/` → схемы, данные, миграции. Язык: русский. |
| `_install/db/` | БД: схемы, данные, тесты | `schema.sql` + `migrations/`. `seed.sql` + `migrations_data/`. `test_data.sql`. Только через ORM/CLI. |
| `config/` | Внешние конфигурации | `.env.example` обязательно. Валидация при старте (Zod/Pydantic). |
| `scripts/` | Утилиты, CI-хелперы | Идемпотентность. Вывод в `stdout`. Запрет `rm -rf`, `DROP DATABASE`. |
| `adr/` | Архитектурные решения | Файлы `ADR-NNN-title.md`. Создаются для решений уровня `🔴 High`. |

🔒 **Правила данных:** Секреты → `.env` / менеджер секретов. Бинарники → `.gitignore` / LFS. Пути только относительные.

## 📝 Принципы документирования (Documentation Principles)
Пути к документации конфигурируются в `.cursor/config.json`. По умолчанию используется `_doc/`. Никогда не хардкодь пути.

1. **Структура по назначению:**  
   `plans/` → Что строить (высокоуровневые планы).  
   `reports/` ↔ `_work/` → Что сделано (итоговые отчёты).  
   `issues/` → Техдолг и известные проблемы.  
   `features/`/`api/`/`components/`/`architecture/` → Детальная документация.  
   `adr/` → Архитектурные решения.  
2. **Гайдлайны наполнения:**  
   - Один файл = одна тема/фича. Не смешивать контексты.  
   - Всегда добавлять дату обновления и ссылку на исходный код.  
   - Использовать кросс-ссылки между связанными документами.  
   - Архивировать устаревшие разделы, не удалять бесследно.  
3. **Нейминг файлов:**  
   - Фичи/планы: `feature-name.md` (kebab-case)  
   - Компоненты: `ComponentName.md` (PascalCase)  
   - Проблемы: `ISS-NNN-description.md`  
   - ADR: `ADR-NNN-title.md`  
4. **Триггеры обновления:**  
   - **Авто:** после завершения оркестрации, фиксов багов, создания ADR.  
   - **Ручно:** по команде `/documenter` или явному запросу пользователя.

## 📋 Планирование и управление задачами (Task Management)
Двухуровневая система: временное состояние (workspace) + перманентный контент (документация).

1. **Идентификаторы оркестрации:** `orch-YYYY-MM-DD-HH-mm-{slug}` (пример: `orch-2026-02-10-15-30-auth`).
2. **Состояние сессии (Workspace):** Хранится в `tmp/active/{id}/`: `progress.json`, `tasks.json`, `links.json`. При крахе → `_tmp/` для `resume`. Автоочистка завершённых через 7 дней.
3. **Лимиты:** Макс. **10 задач** за цикл. При приближении к лимиту токенов → сохранение состояния + запрос продолжения.
4. **Статусы:**  
   - Оркестрация: `🔵 planning` → `🟢 ready` → `🟡 in-progress` → `🟠 documenting` → `✅ completed` / `❌ failed`  
   - Задача: `⏳ pending` → `🔄 in-progress` → `✅ completed` / `🚫 blocked`  
5. **ID задач:**  Формат  `PREFIX-NNN`  ( `AUTH` ,  `PAY` ,  `API` ,  `UI` ,  `DB` ,  `REF` ,  `TEST` ). Описания → русский, ID → английский.
6. **Issues (Техдолг):** Создаются только для некритичных проблем. Формат: `ISS-NNN-description.md`. Не блокируют текущую работу.

## 🔄 Правила обработки запросов (Workflows)

### 🟢 Простые задачи: `/implement` (Code → Test → Docs)
**Применение:** 1–2 файла, фиксы, компоненты, утилиты, правки конфига.
1. `worker` → генерация кода.
2. `test-runner` → линт + тесты + проверка acceptance criteria.  
   - При падении: вызов `debugger` (макс. 2 попытки) → повтор `test-runner`.  
   - Если тестов нет → шаг пропускается.
3. `documenter` → создание/обновление документации **на русском**.
4. Коммит + отчёт в `_work/` + очистка `tmp/`.

### 🟡🔴 Сложные задачи: `/orchestrate` (Plan → Loop → Docs)
**Применение:** Полноценные фичи, мульти-модули, рефакторинг, архитектура, миграции.
1. **Phase 1: Планирование** → `planner` разбивает задачу (макс. 10 за цикл). План в `tmp/plan.md` и линкуется в `_doc/plans/` **на русском**.
2. **Phase 2: Цикл задач** (для каждой подзадачи):
   - `worker` → реализация.
   - `test-runner` → линт + тесты + проверка критериев. ❌ Ошибка/неполнота → `debugger` (макс. 3 попытки).
   - `security-auditor` → проверка (аутентификация, ввод, секреты, платежи).
   - `reviewer` → проверка качества. ❌ Замечания → `debugger` (макс. 3 попытки).
   - ✅ Успех → статус задачи `completed`, переход к следующей.
3. **Phase 3: Документация** → `documenter` формирует отчёт **на русском**, сохраняет в `_work/`. Очистка `tmp/`.
⚠️ *Лимит контекста:* при приближении → сохранение в `_tmp/`, запрос продолжения у пользователя.

## 🏛 Архитектурные принципы (Architecture Principles)

| Принцип | Ключевые правила |
|---|---|
| **SOLID** | SRP (один модуль = одна причина изменения), OCP (открыто для расширения, закрыто для модификации), LSP (подтипы не ломают контракт), ISP (узкие интерфейсы), DIP (зависим от абстракций). |
| **Слои (SoC)** | Presentation → Application → Domain → Data → Infrastructure. Зависимости направлены внутрь. Бизнес-логика изолирована. |
| **Паттерны** | **Repository** (абстракция доступа к данным), **Service** (бизнес-логика), **Factory** (создание объектов), **Strategy** (взаимозаменяемые алгоритмы). |
| **Dependency Injection** | Внедрение через конструктор или `inject()`. Запрет `new` внутри классов. Обеспечивает слабую связность и тестируемость. |
| **Обработка ошибок** | Централизованная. Специфичные типы ошибок (`ValidationError`, `NotFoundError`). Явная обработка `null`. Глобальный обработчик. |
| **Производительность** | Индексы, пагинация, connection pooling, избегание N+1, кэширование на правильном слое, async/await для I/O, очистка ресурсов, таймауты. |
| **Тестирование** | Пирамида: Unit (много) → Integration (некоторое) → E2E (мало). Бизнес-логика тестируется изолированно. |
| **Анти-паттерны** | ❌ God Object, Spaghetti Code, Magic Numbers, Circular Dependencies, Premature Optimization. |

## 🔍 Стандарты качества кода (Code Quality Standards)

| Категория | Правила |
|---|---|
| **Читаемость** | Понятные имена (англ.), функции ≤ 30 строк, один уровень абстракции. Комментарии **на русском** объясняют «почему». |
| **DRY / KISS / YAGNI** | Выноси общую логику. Простое решение лучше сложного. Не добавляй функционал «на будущее». |
| **Code Smells** | Длинный метод → Extract Method. Большой класс → Split (SRP). Много параметров → Parameter Object. Примитивная одержимость → Value Objects. Дублирование → Shared Utils. |
| **Best Practices** | Иммутабельность (копирование вместо мутации). Чистые функции (без сайд-эффектов). Конфигурация централизована. |
| **Метрики сложности** | Cyclomatic Complexity: 1–5 (норма), 6–10 (умеренно), 11–20 (высоко, рефакторинг), 21+ (критично, обязателен рефакторинг). |

## 🌿 Версионирование и Git-практики (Git & Versioning)

### Инициализация и настройка
Репозиторий: `.git/` в корне решения. Ветка по умолчанию: `main`.

```bash
git init
git remote add origin <url>
```

### Workflow после успешной реализации

**Шаг 1 — проверка перед коммитом:**
```bash
git status                                      # что изменилось
dotnet build EngineeringPerformance.Legacy.slnx        # сборка green
dotnet test EngineeringPerformance.Legacy.slnx         # все тесты green
```

**Шаг 2 — стейджинг:**
```bash
git add .                                       # или точечно: git add <file>
git status                                      # финальная проверка
```

**Шаг 3 — коммит (Conventional Commits):**
```bash
git commit -m "feat(scope): subject"
# тело коммита при необходимости — русский язык
```

**Шаг 4 — пуш:**
```bash
git push origin <branch>
```

### Именование веток

| Тип | Шаблон | Пример |
|-----|--------|--------|
| Новая фича | `feat/<description>` | `feat/projects-page` |
| Баг-фикс | `fix/<description>` | `fix/performance-filter` |
| Рефакторинг | `refactor/<description>` | `refactor/data-import` |
| Документация | `_doc/<description>` | `_doc/git-workflow` |
| Задача/обслуживание | `chore/<description>` | `chore/update-deps` |

### Типы коммитов

| Тип | Когда |
|-----|-------|
| `feat(scope)` | новая функциональность (фича, UI, сервис) |
| `fix(scope)` | исправление бага |
| `refactor(scope)` | рефакторинг без изменения поведения |
| `test(scope)` | добавление/изменение тестов |
| `docs(scope)` | документация, CHANGELOG, `.md` файлы |
| `chore(scope)` | зависимости, конфиги, инфраструктура |
| `perf(scope)` | оптимизация производительности |

**Scopes проекта:** `app`, `core`, `infra`, `tests`, `db`, `ui`, `docs`, `config`

### Правила коммита

- Заголовок: **английский**, строчные, без точки, ≤ 50 символов
- Тело (опционально): **русский**, объясняет «почему», не «что»
- Каждый коммит компилируется и тесты проходят
- `_doc/changelog/CHANGELOG.md` обновляется **в том же коммите**, что и код
- При изменении схемы БД — миграция и SQL-скрипт в одном коммите с кодом

### Ветковая стратегия

```
main          ← production-ready, теги v1.x.x
  └── feat/*  ← фичи, мержатся через PR
  └── fix/*   ← фиксы, мержатся через PR
```

- **Прямой пуш в `main` запрещён** (только через PR/merge)
- `rebase` — для локальных веток перед PR
- `merge --no-ff` — для интеграции в `main`

### Теги релизов (SemVer)

```bash
git tag -a v1.0.0 -m "Первый релиз"
git push origin --tags
```

`BREAKING CHANGE:` в теле коммита → мажорный релиз (v2.0.0).

⛔ **Запрещено:**
- `git push --force` в `main`
- Коммитить `bin/`, `obj/`, `.vs/`, `*.user`, `tmp/`, секреты
- Коммитить без прохождения `dotnet test`

## 🤖 AI Instructions
1. **Типы & Валидация:** всегда добавляй строгую типизацию, валидацию ввода и централизованную обработку ошибок.
2. **Зависимости:** не предлагай новые пакеты без явного запроса.
3. **Архитектура:** при изменении структуры сначала опиши план в `tmp/session_plan.md`, для `🔴 High` запроси подтверждение и создай ADR.
4. **Стиль:** следуй линтер-конфигам, `.editorconfig`, принципам SOLID, DRY, KISS, YAGNI. Для Angular используй Standalone Components, OnPush, Signals и новый Control Flow.
5. **Документация:** `_doc/` и `_install/` обновляются **в каждом коммите**, где затрагивается логика, API, БД или UX. **Язык: русский**. 1 файл = 1 тема.
6. **Планирование & Состояние:** двухуровневое отслеживание (`tmp/` для состояния, `_doc/` для контента). Лимит 10 задач/цикл. При крахе → `_tmp/` + `resume`.
7. **Git:** Conventional Commits (**заголовок на английском**). Запрет прямого пуша в `main`. Rebase локально, Merge в продакшн.
8. **Контекст & Ограничения:** следи за лимитом токенов. При приближении сохраняй состояние и запрашивай продолжение. При расхождениях → остановись и укажи на конфликт.
9. **Языковая политика:** Документация, планы, отчёты, комментарии → **русский**. Код, имена, технические запросы, коммиты → **английский**.
10. **Инфраструктура:** при изменении деплоя обнови `DEPLOY.md` и `docker-compose.yml`. Все изменения инфраструктуры требуют `🔴 High` оркестрации.
