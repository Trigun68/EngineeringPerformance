# ADR-002: Журнал действий пользователей

**Дата:** 2026-05-09
**Статус:** Предложено (ожидает подтверждения пользователя)
**Авторы:** Elise

---

## Контекст

В приложении нет аудита действий пользователей. Для эксплуатации (несколько ролей: Admin / Manager / Observer) нужно фиксировать ключевые события, чтобы при инцидентах/спорах было понятно «кто что и когда сделал».

Запрос пользователя:
1. Логировать действия в БД.
2. На странице «Настройки» — третья вкладка «Журнал действий» с просмотром.
3. Кнопка «Сохранить в файл и удалить из БД» (архивирование).
4. Кнопка «Восстановить из файла в БД».

## Решение

### Что логируется (по согласованию)
- Login/Logout (включая `LoginFailed`).
- CRUD проектов и версий анализа.
- Импорт и удаление физ. объёмов (ФО) и трудоёмкости.
- Редактирование строки детальной сетки (физ.объём / номенклатура / норма IIC).

**Только метаданные** (кто/что/когда/над какой сущностью). Старые/новые значения **не сохраняются** — снижение объёма БД, отказ от полного аудита.

### Схема — новая таблица `UserActionLogs`
| Поле | Тип | Описание |
|---|---|---|
| `Id` | `int IDENTITY PK` | первичный ключ |
| `UserId` | `int FK Users.Id (Restrict)` | автор (NULL для оркестратора/системных событий не используется — Restrict) |
| `Timestamp` | `datetime2(3)` UTC | время события |
| `ActionType` | `nvarchar(64)` | значение enum `UserActionType` (стринг для читабельности в БД) |
| `EntityType` | `nvarchar(100) NULL` | имя класса сущности (`Project`, `ProjectAnalysisVersion`, `ProjectPhysicalVolume`, …) |
| `EntityId` | `int NULL` | id затронутой записи |
| `Description` | `nvarchar(500) NULL` | человекочитаемое уточнение (например, имя проекта, номенклатура ФО) |
| `IpOrHost` | `nvarchar(64) NULL` | имя машины (Environment.MachineName) |

**Индексы:**
- `IX_UserActionLogs_UserId_Timestamp` (UserId ASC, Timestamp DESC) — для просмотра «последние действия пользователя».
- `IX_UserActionLogs_ActionType` — фильтрация по типу.
- `IX_UserActionLogs_EntityType_EntityId` — поиск действий над сущностью.

### Файловый формат экспорта/импорта
**CSV** с заголовком: `Id;UserId;UserName;Timestamp;ActionType;EntityType;EntityId;Description;IpOrHost`. Разделитель — `;` (Excel-friendly RU). Кодировка — UTF-8 BOM. Экранирование стандартное (RFC 4180).

`UserName` пишется в файл (информационно), но при импорте используется только `UserId`. Если `UserId` нет в БД — строка пропускается с отчётом.

### Дедупликация при импорте
Ключ дубликата: `(UserId, Timestamp, ActionType, EntityType, EntityId)`. Совпадения **пропускаются** с записью в отчёт импорта.

### Безопасность / доступ
- Просмотр / экспорт / импорт — только Admin (`AccessControlService.CanRead(user, "UserActionLog")` + Edit для экспорта/импорта).
- Поле `Settings`/`Users` уже существует в `AccessControl`; добавим тип доступа `UserActionLog`.

### Архитектура
- **Core**: enum `UserActionType`, DTO `UserActionLogDto`, интерфейс `IUserActionLogService`, фильтр-DTO `UserActionLogFilter`.
- **Infrastructure**: `UserActionLog` entity + `UserActionLogConfiguration` + EF миграция + SQL-дубль; `UserActionLogService` с методами Log/Get/ExportToCsvAndPurge/ImportFromCsv.
- **App**: `UserActionLogView` + `UserActionLogViewModel`, регистрация третьей вкладки в `SettingsPageViewModel.BuildTabs` после «Права пользователей»; внедрение `IUserActionLogService.LogAsync(...)` в ключевые команды.

### Что НЕ делаем сейчас (намеренно)
- **Авто-архивация** (по расписанию / по достижению порога) — вынесено в `_doc/issues/ISS-001-user-action-journal-auto-archival.md` как backend-задача на будущее.
- **Old/New value capture** — отказались осознанно ради компактности БД и быстрой реализации.
- **Логирование чтений** (просмотров) — only writes/state changes.

## Альтернативы (рассмотрены)
- **Serilog → файл**: уже есть, но не структурно, не фильтруется в UI, нет ID-привязки к пользователю в БД. Не закрывает запрос.
- **EF SaveChanges interceptor с автологом всех изменений**: слишком шумно, ловит технические изменения (миграции, seed). Отвергнуто.
- **NoSQL/Elastic для логов**: оверкилл для текущего масштаба (≤10 пользователей).

## Риски и компенсации
| Риск | Компенсация |
|---|---|
| Расширение БД от логов | Ручной экспорт + удаление (экспорт обязателен перед DELETE). Авто-архив — отдельная задача. |
| Производительность `LogAsync` блокирует команды | `LogAsync` не критичная: ошибка пишется в Serilog, но не ломает основную операцию (try/catch вокруг). |
| FK на `Users.Id` (Restrict) ломает удаление пользователя | На текущем этапе пользователи не удаляются, помечаются неактивными. Если потребуется — миграция на `SetNull` + `UserId NULL`. |
