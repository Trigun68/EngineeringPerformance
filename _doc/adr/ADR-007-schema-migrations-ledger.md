# ADR-007: Журнал `dbo.SchemaMigrations` и политика неизменяемых SQL-миграций

**Дата:** 2026-09-08  
**Статус:** Accepted  
**Авторы:** команда Engineering Performance

---

## Контекст

Схема БД задаётся SQL-скриптами `migrations/schema/NNN_*.sql` (не EF Migrations); применяет их контейнер `ep-db-init` (`scripts/docker-db-init.sh`) при каждом `docker compose up`.

До сентября 2026 скрипт держал **два ручных списка**: `SCHEMA_FILES` для пустой БД и отдельный список для существующей БД, который на каждом старте заново выполнял `017`, `017b`, `099–106` и всё, что добавили руками. Проблемы:

- новый файл, забытый в одном из списков, не применялся (или применялся только на чистой БД);
- нет истории «что и когда применено» на конкретном окружении;
- `001–016` на живой БД не переигрывались, но и не фиксировались — нельзя было отличить «применено» от «пропущено»;
- правка уже применённого файла молча расходилась между окружениями;
- `017a_RecreatePhysicalVolumesForRecovery.sql` (пересоздание ФО для восстановления) был в общем списке.

## Варианты решения

### Вариант A: журнал `dbo.SchemaMigrations` + glob по каталогу + checksum

Таблица `SchemaMigrations(ScriptName PK, AppliedAtUtc, Checksum char(64))` (`000_SchemaMigrations.sql`). Скрипт обходит `migrations/schema/*.sql` в C-locale сортировке; применённые (есть запись) пропускаются, новые — выполняются и штампуются с SHA-256. Baseline `001–016` на существующей БД штампуется **по свидетельству** (таблица/колонка/длина есть → штамп; нет → выполнить). Несовпадение checksum у применённого файла → init падает. `017a` — только при `RECOVERY_RECREATE_PPV=1`.

**Плюсы:** один источник — файловая система; история на окружении; защита от правки задним числом; recovery-скрипт не запускается случайно.  
**Минусы:** нужно один раз пройти bootstrap на каждом окружении; редактировать применённый файл нельзя даже для комментария.

### Вариант B: перейти на EF Core Migrations

**Плюсы:** стандартный `__EFMigrationsHistory`.  
**Минусы:** ~120 существующих T-SQL скриптов с данными/индексами/recovery-логикой пришлось бы переписывать; смешение двух историй на живых БД; отдельный процесс генерации на dev-машинах без SQL.

### Вариант C: оставить ручные списки, добавить только идемпотентность скриптов

**Плюсы:** ничего не менять в инфраструктуре.  
**Минусы:** не решает забытые файлы и отсутствие истории; повторный прогон десятков скриптов на каждом старте.

## Решение

**Выбран вариант A.**

Правила:

1. Применённый скрипт **не редактируется**. Любое изменение схемы — новый файл со следующим номером (в т.ч. «добавить индекс, если таблица уже была» — см. `122_*`).
2. Скрипты идемпотентны (`IF NOT EXISTS` / `IF COL_LENGTH(...) IS NULL`): защита на случай ручного запуска вне журнала.
3. `001_InitialSchema.sql` — только на пустой БД; `001–016` на существующей БД — штамп по свидетельству (`baseline_evidence_present`), при отсутствии свидетельства выполняются.
4. Checksum: при первом запуске после внедрения дозаписывается для уже заштампованных строк; далее расхождение = ошибка init с именем файла.
5. `017a_RecreatePhysicalVolumesForRecovery.sql` — только с `RECOVERY_RECREATE_PPV=1`, без штампа при пропуске.
6. `data/*.sql` (сиды) — вне журнала, остаются идемпотентными.

## Последствия

### Положительные
- Новая миграция = один файл; ничего не нужно регистрировать в скрипте.
- `SELECT * FROM dbo.SchemaMigrations` показывает состояние окружения.
- Бэкапы/восстановление (`RESTORE … WITH REPLACE`) не ломают init: журнал едет вместе с БД.

### Отрицательные / Риски
- Ошибка в свидетельстве baseline может привести к повторному прогону раннего скрипта — поэтому свидетельства перечислены явно и только для `008–016`.
- Разработчик, поправивший старый файл «для красоты», получит красный init — это ожидаемое поведение.

### Нейтральные
- EF-модель проверяется отдельно стражем `EfSchemaSmokeTests` (модель ↔ `INFORMATION_SCHEMA`), журнал не заменяет этот тест.
