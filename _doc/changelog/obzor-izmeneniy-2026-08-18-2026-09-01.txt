1. КРАТКО: ЧТО ИЗМЕНИЛОСЬ ДЛЯ ПОЛЬЗОВАТЕЛЯ
========================================================================

За две недели продукт перешёл от «гриды + табличный PDF» к отчётной
и аналитической поверхности: визуальные PDF, переработанная вкладка
«Отчет», четыре вкладки аналитики по мокапам, справочник стоимости
работ в рублях, новая формула нормы «Логнормальное распределение», единое написание
БЕР, заметно быстрее открытие больших проектов.

Главное, что видно в интерфейсе:

  • Вкладка проекта «Отчет»: сводный дизайн план/факт, шкала Z, динамика
    версий, подвкладка «Тренд», визуальный PDF.
  • Аналитика: «Тренд оценки», «Тренд оценки производительности»,
    «Анализ факта и норм», «Анализ норм» + справка и «Тренд часов».
  • Справочники: «Стоимость работ» (₽/ч по группам IIC), формула
    «Логнормальное распределение» в нормах IIC, «БЭР» везде заменено на «БЕР».
  • PDF прогноза/факта/отчёта — обложка, KPI, графики, единый внешний вид.
    Детальный PDF на десятки тысяч строк убран (остался Excel).
  • Открытие проекта быстрее: меньше данных по сети, детальный грид
    грузится только на вкладке «Детально», шапка не пропадает.
  • Подписи кнопок выгрузки единые: «Выгрузить Excel / PDF».
  • Двойной щелчок в списках норм и стоимости открывает редактор записи.

2. НОРМЫ IIC И СПРАВОЧНИКИ
========================================================================

2.1. Формула «Логнормальное распределение» (31.08, коммит 61891fc;
     подпись UI с 01.09 — раньше «Кривая Кима»)

  Новый тип формулы нормы групп физобъёмов (IIC): логнормаль.

  Смысл:
    производительность P > 0, σ > 0 в логарифмическом пространстве;
    μ = ln(P) считается автоматически и только для чтения;
    P(z) = e^(μ + z·σ);
    плановые часы LI(z) = P(z) × эффективный объём.
    При z = 0 часы совпадают с постоянной нормой (P × V).

  Что хранится в регистре:
    Performance = P, Estimate = μ, StandardDeviation = σ (лог, не доля × P).
    Для линейных норм по-прежнему StandardDeviation = σ_отн × P.

  Интерфейс:
    в редакторе, гриде, карточке анализа норм и Excel-реестре видны
    три подписи: Производительность, μ, σ. Для логнормального типа скрыт блок
    «отклонение от нормы, %».

  Что специально НЕ сделано:
    массовый пересчёт всех версий проектов при появлении типа формулы
    запрещён. Старые нормы и снимки версий не трогаются. Тип проверяли
    на новой группе и новом периоде, чтобы as-of снимки не подхватили
    его задним числом.

  Анализ факта и норм (FactNorm):
    этого типа нет в каталоге BIC (по-прежнему 7 типов). Если текущая норма
    уже логнормальная, σ факта считается как стандартное отклонение ln(Y).

  Документация: ADR-005, forecast-algorithm, hours-and-z-ssot,
  _doc/api/iic-norms.md. Миграции SQL под enum не нужны (int без CHECK).

2.2. Справочник «Стоимость работ» (29.08)

  Новая вкладка сразу после «Нормы физобъёмов (IIC)».
  Ставка ₽/ч по дереву групп IIC. Версионность только датой
  «действует с / по» (как у норм).

  Слева — список дат установки расценок:
    клик открывает блок этой даты в дереве;
    двойной клик (или «Изменить») — правка всего блока;
    «Удалить» снимает период, предыдущий продлевается.
  «Задать стоимость» — новый период (уровень: организация / 1 / 2 /
  каждый элемент; сервер раскладывает ставки по дереву).
  Дата внутри уже закрытого интервала закрывает блок днём до следующего.

  Право: EngineeringWorkCosts.
  Выгрузка: справочник_стоимость_работ.xlsx.
  Миграция: 115_WorkDirectionWorkCosts.sql.

  На обложке PDF прогноза («Итого» и «По объектам») под каждым
  сценарием (оптимистичный → базовый → пессимистичный) выводится
  стоимость в ₽: ставка на дату версии × трудоёмкость направления.
  На внутренних страницах PDF рублей нет.

2.3. Написание «БЕР» (28.08)

  Во всём приложении, API, сидах и документации «БЭР» заменено на «БЕР».
  Тип в PhysicalVolumeTypes обновляется миграцией
  114_RenameBerTypeSpelling.sql. Переписаны сиды номенклатуры ФО.

2.4. Двойной щелчок в редакторах (31.08, коммит 4b2392e)

  В модалке «Редактирование нормы» двойной щелчок по строке периода
  открывает карточку записи — то же, что кнопка «Редактировать»
  (как в WPF EditHistoryItemCommand).

  Справочник «Стоимость работ»: двойной щелчок по дате периода или
  по группе в дереве открывает правку блока.

  Диалог выбора проекта: двойной щелчок подтверждает выбор
  (как кнопка «Выбрать»). Диалог выбора версии анализа по-прежнему
  выбирает версию, а не открывает карандаш — иначе ломается смена версии.

2.5. Прочие правки справочников и терминологии (24–25.08)

  В пользовательском тексте «ИИС» / «EAC» / «EES» заменены на «IIC»
  (дашборд, КФО/БЕР, меню норм, предупреждения, сообщения API).
  Имена классов и маршрутов API не менялись.

  Формат имени группы IIC везде один: «код — наименование (ед.)».
  HierarchicalSelect по умолчанию больше не подставляет IIC-формат
  туда, где его быть не должно (например, каталог оборудования).

  «Сводный вер 1» по мокапу ReportRedesignMockup:

    план из основной факт-версии (её BaseHours), иначе из основной план;

  −0,86 из диалога планирования.

  Динамика Z: точки плана с Z и трудоёмкостью; одна точка основной
  факт-версии; ось X — даты; в подсказке — Z и часы трёх сценариев.

  Визуально: слева хуже (+3 / Критично), справа лучше (−3 / Отлично).

  Числа в таблицах и оси графиков не пересчитывались — инвертирован
  только рисунок шкалы (сводный вер 1/2, PDF, превью /dev/pdf-mockups).

  Пастельная полоса зон, подписи под полосой. Пороги зон те же:
  −1 / −0.5 / 0.5 / 1.

3.3. PDF отчёта по проекту

  Новая выгрузка export/report/pdf — визуальный «Отчёт по проекту —

    ComputeProductivityIndex; строки без объёма/нормы/часов выкидываются

  Старые секции не удалены, убраны в «Дополнительно»:

    у производительности — смена формул N(V*) и таблица переходов.

  На демо-контуре факт-индекс и факт-Z часто пустые: у факт-версии
  25-310 все 1008 строк трудоёмкости без WorkDirectionId; у 25-970
  LI нет. План-индекс при этом считается (~163–177%). Это согласовано
  с вкладкой «Отчет», а не регрессия расчёта.

4.3. Две поверхности «Тренд» проекта и портфеля (27.08)

  Проект → Отчет → «Тренд»:
    срез — основная факт-версия (+ основная план для моста часов);
    история — все неархивные версии проекта;
    чипы версии, динамика Z, мост часов по корневым группам IIC
    (эффект объёма и эффект производительности), столбцы Z от 0,
    S-curve часов факта; водопад ΔZ — в «Дополнительно».
    API GET /api/projects/{id}/report-trend (право Reports).

  Аналитика → «Тренд оценки»:
    первый экран — четыре блока портфеля (Z по датам, мост часов,
    сетка Z от 0 с осью «проекты», S-curve). KPI «было/стало» и таблица
    версий с первого экрана убраны.

  Мост часов считается только в движке:
    hoursAtPlanRate = H_план × (V_факт / V_план);
    volumeEffect + productivityEffect = H_факт − H_план.
    Клиент формулу не дублирует.

4.4. Добор тренда: покрытие, вехи, «кто тянет», выгрузки (28.08)

  Покрытие часов (ComputeHoursCoverage): чипы «Z известен» и

  Полоса p10–p90 вокруг среднего Z; линия портфеля; вехи версий

  Таблица «кто тянет» — вклады последнего факт-среза; клик ведёт

  «Анализ факта и норм».

  S-curve плана рядом с фактом; в «Дополнительно» аналитики —
  тонкие линии топ-проектов + «Прочие».

  Сырой Δ часов под мостом (не вместо эффектов объёма/производительности).
  Водопад ΔZ плана на первом экране.

  Выгрузки отчет_тренд / аналитика_тренд (Excel и PDF).

  Мост аналитики берёт основной план проекта даже вне периода фильтра;

5.1. Визуальный движок «Executive Technical» (25–27.08)

  Тёмная обложка с KPI и Z-шкалой, блоки автоматических выводов
  (PdfInsightBuilder), графики ScottPlot, тема ReportVisualTheme.

  На рабочую область переведены:
    прогноз Итого, факт Итого, факт По объектам, анализ версии,
    прогноз По объектам (последняя кнопка, которая ещё отдавала
    табличный PDF).

  Правила оформления (закреплены правилами репозитория):
    сценарии всегда Оптимистичный → Базовый → Пессимистичный;
    полные названия, без «Опт.» / «Пессим.»;
    тёмный шрифт на контенте (белый только на титуле);
    заливка столбцов как в гриде: #e3f2fd / #e8f5e9 / #ffebee;
    числа ru-RU: объём и часы — 1 знак, производительность и Z — 2;
    выравнивание вправо;
    IIC только как «код — наименование (ед.)», без колонки «Код»;
    аббревиатура IIC, не «ИИЦ»;
    время на обложке и в футере — московское (MSK), не UTC.

  Прогноз «По объектам»: на титул добавлены KPI трёх сценариев,
  как на «Итого».
  Факт «По объектам»: график подписан «Фактические часы по объектам».
  Сравнение «Детально»: кнопка PDF скрыта.

  /dev/pdf-mockups — превью темы, только для администратора
  (раньше страница была публичной).

5.2. Детальный PDF отключён (26.08)

  Полная детализация на десятки тысяч строк давала PDF на 13k+ страниц
  (~100 МБ) и роняла вкладку браузера. Кнопки PDF на «Детально»
  (прогноз и факт) и соответствующие API удалены. Данные остаются

5.3. Единые имена файлов (22.08 и далее)

  Шаблон: {модуль}_{вкладка}[_{уточнение}]_-_{код}_{название}_({версия}).ext

  Имя задаёт сервер в Content-Disposition. Клиент не подменяет его
  английским fallback. Дату в имя не добавляют.

5.4. Подписи кнопок выгрузки (24.08)

  Везде одинаково: «Выгрузить Excel», «Выгрузить PDF»,
  «Выгрузить Excel (выделенное)», «Выгрузить Excel (сводная)»,
  «Выгрузить CSV».
  Вид: outlined, small, без uppercase. Пока идёт запрос — тот же текст,

  Импорт версии: «Импорт ФО / оборудования / трудоёмкости» без сокращений.

6. РАСЧЁТ ЧАСОВ И Z (ЕДИНЫЙ ДВИЖОК)
========================================================================

Вся математика — только PerformanceCalculationEngine. Сервисы грузят
данные, вызывают движок, мапят DTO. Параллельных формул в UI, импорте
и контроллерах быть не должно.

Что закрепили за две недели:

  • Плановые часы на прогнозе, факте, сравнении, в отчёте и аналитике
    считаются одним алгоритмом: норма по сценарию версии
    (по проекту / по объекту / по строке), затем три варианта Z.
    В группировку входят только строки с оценкой «Да».

  • С 24.08 плановые часы пишутся в колонки БД одним прогоном движка
    (LaborIntensity* на ФО и оборудование), гриды читают сохранённое.
    Пересчёт после импорта Excel, CRUD строк, смены сценария/Z, правки
    норм IIC (только затронутые версии). Массовый backfill:
    scripts/recalculate-all-labor.sh.

  • Часы факта в агрегации — разнесённые плановые трудоёмкости
    (PlannedHours), а не ActualHours ввода.

  • Тренд Z всегда взвешивается по часам (равный вес убран).

  • Порядок колонок плановых часов везде: оптимистичный → базовый →
    пессимистичный (в сравнении сначала версия A, затем B). То же
    в Excel/PDF.

  • 21.08: плановые часы на оценке факта, в сравнении и в отчёте
    совпадают с ИТОГО прогноза (live N(V)×Z по ФО и оборудованию).
    Копия версии наследует снимок норм источника.

8. ПРОИЗВОДИТЕЛЬНОСТЬ, КЭШ, ИНФРАСТРУКТУРА

8.1. Объём данных проекта (18–20.08)

  Ответ page-data: 48.2 МБ → 6.47 МБ (после сжатия сети 2.24 → 1.07 МБ).
  Повторное открытие: ~0.4–0.9 с вместо 1.24 с.

  Гриды «Детально» едут колоночно: имена полей и повторяющиеся строки
  один раз, в ячейке — индекс. Состав столбцов не менялся.
  Упаковка на HTTP-границе; внутренний DTO для Excel/PDF прежний.

  Таблицы «Итого» и «По объектам» больше не тащат десятки тысяч
  детальных строк: детальный грид догружается при переходе на вкладку.

  Справочники: ETag / 304, если не менялись.
  Статика: hashed JS/CSS кэшируются на год (immutable); index.html
  не кэшируется; gzip заранее.

  Уход со страницы во время расчёта больше не даёт 500: запись кэша
  не привязана к токену отмены запроса.

8.2. Оболочка приложения (20.08)

  Меню и шапка не исчезают при первом заходе в аналитику, справку,
  админку и настройки: крутилка только в карточке страницы
  (Suspense вокруг Outlet, а не вокруг всего AppLayout).

8.3. SQL и кэши аналитики (23–25.08)

  Auth / refresh / preferences не делят пул с холодным page-data:
  EP-Interactive (Min 2) и EP-Analytics (Max 8).
  Таймаут SQL → HTTP 503 sql_unavailable, без тройного лога EF.

  SQL-профилирование по умолчанию выключено (SqlProfiling__Enabled=false).

  Кэши трендов — generation-ключи IProjectAnalyticsCache: мутация
  проекта сразу сбрасывает портфельные выборки.

  Устранены N+1: пакетная загрузка версий (LoadManyAsync,
  EvaluateManyAsync); сводный отчёт предзагружает историю одним батчем.

  Сравнение версий считается один раз на пару и кладётся в кэш
  поколения; клиент строит диаграмму из summary без второго тяжёлого GET.

8.4. Docker и переезд исходников (19.08)

  Имя Compose-проекта зафиксировано: engineeringperformance.
  Перенос каталога с кодом больше не создаёт второй том SQL.
  В новой папке: docker compose up -d без down -v и без --build,
  если код не менялся.

  Healthchecks: backend /api/health, frontend /.

8.5. E2E и CI (18.08 и 28.08)

  Playwright на GitHub Actions не критерий (нет средств / billing).
  Агент гоняет E2E локально на docker-стеке http://127.0.0.1:8081,
  не через Vite :5173.

  Ограничен hang apt при установке браузеров Playwright в CI
  (таймаут 20 мин, один повтор).

11. НЕЗАКОММИЧЕННАЯ РАБОТА НА 1.09
   (ветка feat/corp-architecture-cycle)
========================================================================

Это ещё не в master. По CHANGELOG и рабочему дереву:

  • Оборудование входит в тот же эффективный объём V_g, что и ФО:
    при группировке по проекту/объекту норма N считается от суммы
    assessed-объёмов. Уже сохранённые часы сами не обновятся —
    нужен «Пересчитать» или scripts/recalculate-all-labor.sh.

  • Плановые объёмы по листу IIC: соседние строки больше не обнуляются.
    В сценарии «каждая позиция» несколько строк ФО по одному направлению
    — ошибка 400. В групповых сценариях V* распределяется пропорционально
    физобъёму.

  • Подписи Z: в гридах и на факте — «Оценка Z»; план в отчёте —
    «Заложенный Z» (параметр планирования, не live-оценка грида).

  • Справочник «Комплекты документации»: импорт трудоёмкости выделяет
    код после «|»; несопоставленные комплекты — карантин (часы не
    попадают в распределение). Миграция 117_DocSets.sql.

  • Лимит Excel 10 МБ (nginx и API). Конкурирующее сохранение версии
    анализа отвечает 409. Журнал пересчёта:
    GET /api/projects/{id}/versions/{vid}/calculation-log.

  • Снимки каталога ФО на версии (116_PpvCatalogSnapshot.sql),
    RowVersion версии анализа (119), валидаторы ingest, разбор
    доверенного прокси SPNEGO в отдельные сервисы.

  • Админка «Ресурсы» (/admin/resources): CPU/RAM бэкенда, Redis и SQL,
    выбор периода «Отчёт за» до 90 суток. Сэмплы в ResourceMetricSamples
    (120_ResourceMetricSamples.sql). Карточки и вердикт — «сейчас»;
    графики — выбранное окно с даунсэмплом.
